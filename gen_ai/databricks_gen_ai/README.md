### From Prompt Engineering to RAG

- **Prompt Engineering Primer**
    - Prompt Engineering is the practice of designing and refining prompts to optimize the responses generated by AI models
    - Prompt components
        - Instruction
            - Directive that specified what model should do
        - Context
            - Additional information to understand the task
        - Input/ question
            - The query that model needs to process
        - Output type/ format
            - The style of response generated by model
    - Prompt engineering techniques
        - Zero-shot/ Few-shot prompting
            - Zero-shot
                - Prompt without providing any examples
            - Few-shot
                - Prompt with a few input-output examples
        - Prompting chaining
            - Multiple tasks are linked together, with the output of one prompt serving as the input for the next
        - Chain-of-Thought prompting
            - CoT prompting enhances the reasoning capabilities of LLMs by guiding to articulate thought process step by step
    - Prompt engineering tips & tricks
        - Prompts are model-specific
            - Different models may require different prompts
            - Provide examples & cues to guide model
            - Different use cases may require different prompts
            - Iterative Development is key
                - Iterate by adjusting temperature parameter
                    - higher for more creative, lower for focused
            - Be aware of bias & hallucination
        - Format prompts
            - Use delimiters to distinguish between instruction & context
                - Pound sign ###
                - Backticks ```
                - Braces/ brackets {} /  []
                - Dashes —--
            - Ask model to return structured output
                - HTML, JSON, table, markdown, etc…
            - Provide a correct example for the output
                - “the output should look like…”
        - Guide model for better responses
            - Ask model not to make things up/ hallucinate
                - “do not make things up if you do not know, say I do not have information”
            - Ask model not to assume or probe for sensitive information
                - “do not make assumption based on nationalities”
                - “do not ask use to provide SSN”
            - Ask model not to rush to solution
                - Ask it to take time to think CoT for reasoning
                    - “explain how to solve this math problem, do this step-by-step, step 1: …, step 2: …, step 3: …
    - Benefits & limitations
        - Benefits
            - Simple & efficient
            - Predictable results
            - Tailored outputs
        - Limitations
            - Output depends on used model
            - Limited by pre-trained model internal knowledge
                - For external knowledge, we use RAG
- **Introduction to RAG**
    - How language models learn knowledge
        - Model pre-training
            - Training an LLM from scratch
            - Requires large datasets (billions to trillions of tokens)
        - Model fine tuning
            - Adapting pre-trained LLM to specific datasets or domains
            - Requires thousands of domain-specific or instruction examples
        - Passing contextual information
            - Combining LLM with external knowledge retrieval
            - Requires external knowledge base
    - Passing context LMs helps factual recall
        - Passing context as model inputs improves factual recall
        - LLM are evolving to accept larger/infinite input token window size
        - Downsides of long text:
            - Higher API cost for input token
            - Longer completion/ inference times
            - Content/documents in the middle may be overlooked (Lost in the Middle effect)
    - RAG
        - Retrieval Augmented Generation
            - A pattern that can improve efficacy of LLM apps by leveraging custom data
            - It is done by retrieving documents relevant to a question or task and providing them as context to augment prompts to LLM to improve generation
        - RAG solved the knowledge gap, this approach enhances accuracy and relevance of responses
    - RAG use cases
        - Q&A chatbots
            - Incorporate LLMs with chatbots for more accurate answers
            - Used to automate customer support & website lead follow-up to answer questions & resolve issues quickly
        - Search augmentation
            - Incorporate LLMs with search engines that augment search results with LLM-generated answers
            - Makes it easier to find information
        - Content creation & summarization
            - Facilitate development of high-quality articles, reports, and summaries using additional context
            - Example: generation of news articles or summarization of lengthy reports
    - RAG workflow
        - Index & embed
            - Embedding model used for creating vector representation of documents and user queries
        - Vector store
            - Specialized to store unstructured data indexed by vectors
            - Vectors can be stored with vector DB, library, or plugin
        - Retrieval
            - Search stored vectors using similarity search to retrieve relevant information
        - Filtering & reranking
            - The process of selecting or ranking retrieved documents before passing as context
        - Prompt augmentation
            - To enhance context via injection of data retrieved from vector store
        - Generation
            - LLM used for generating response for user’s request
    - Databricks features
        - Delta live tables (batch/stream ingestion)
        - Mosaic AI model serving (embeddings):
            - Foundation models
            - External models
            - Custom models
        - Mosaic AI vector search
        - Unity catalog’s model registry
    - Benefits of RAG architecture
        - Up-to-date & accurate responses
            - LLM responses are not based on static training data
            - Model uses up-to-date external data sources to provide responses
        - Reducing inaccurate responses or hallucinations
            - RAG attempts to mitigate the risk of producing hallucinations or incorrect information
            - Outputs can include citations of original sources, allowing human verification
        - Domain-specific contextualization
            - Can be tailored to interface with proprietary or domain-specific data
            - Improves accuracy of response by using contextually relevant information
        - Efficiency & cost-effectiveness
            - Offers an alternative to fine-tuning LLMs by enable in-context learning without the up-front overhead of fine-tuning
            - Beneficial where models need to be frequently updated with new data

    - **2: Data extraction & chunking**
        - Ingesting documents & making them searchable
            - Split documents into chunks
            - Embed the chunks with a model
            - Store them in a vector store
        - Constraints/ Risks
            - Chunks can be out of context
            - No overall logic/ rigor
        - How to chunk data
            - Semantic chunking
                - Chunk by sentence, paragraph, section
                - Leverage special punctuation such as “\n”
                - Include/inject metadata, tags, titles
            - Fixed-size chunking
                - Divide by specific number of tokens
                - Simple & computationally cheap method
        - Chunking strategy
            - How long the documents are
                - 1 sentence?
                - N sentences?
            - If 1 chunk = 1 sentence
                - embeddings focus on specific meaning
            - If 1 chunk = multiple paragraphs
                - embeddings capture broader theme
            - Chunk overlap
                - Defines the amount of overlap between consecutive chunks, ensuring no contextual information is lost between them
            - Windowed summarization
                - Is a context-enriching chunking method where each chunk includes a windowed summary of previous few chunks
            - Prior knowledge of user’s query patterns can be helpful
                - The goal is to ensure the way information split & indexed leads to maximum retrieval quality
        - Advanced chunking strategy
            - Summarization
                - Overlapping small chunks increase storage and computational demands
                - Summarize larger sections or paragraphs with LLM and then generated embeddings from that
                - Raptor apply this technique to maintain efficiency without sacrificing context
            - Summarization with metadata
                - Include section-specific details along with summary, such as section names, image captions or key metadata
        - Data extraction & chunking challenges
            - Text mixed with image
            - Irregular placement of text
            - Color encoded focus (important for context)
            - Chart with hierarchical information (keeping order of information is critical)
            - Multi-column text (order of columns is crucial)
            - Keep images with related information is crucial
        - The are many tool like LangChain for strategizing document chunking
        - General approaches to address unstructured/complex raw text documents
            - Traditional approach
                - Libraries
                    - PyMuPDF
                - Features
                    - Breaks down text into raw constructs
                    - Very low-level requires hard coding rules
            - Use a layout model
                - Libraries
                    - HF’s LayoutLMv3
                    - doctr
                    - PyPDF
                    - Unstructured
                - Features
                    - Apply deep learning models built to do text extraction and context extraction
            - Multi-modal models
                - Models
                    - GPT-4o and beyond
                    - Gemini1.5 and beyond
                    - Other OSS models
                - Features
                    - Multimodal LLMs understand images but still experimental
    - **3: Embedding model**
        - Embedding
            - A numerical representation of content
            - Text embeddings
                - Are high-dimensional vectors produced by neural network models that convert any text
        - Choosing embedding models
            - Data/Text properties
                - Vocabulary size in the text/documents (some models handle more diverse words)
                - Domain/Topic (i.e. finance, medical, etc…)
                - Text length: typical length of chunks/docs to be embedded
            - Model capabilities
                - Multi-language support
                - Embedding dims/sizes: more storage cost for higher dimensions
            - Considerations:
                - Be aware of context window limits, many embedding models will ignore text beyond their context window limits
                - Privacy and cost/licensing when using proprietary API-based models
                - Benchmark multiple models & choose the one that strikes the best balance
            - Tips
                - The embedding model should represent both queries and documents
                    - Is current embedding model trained on similar data as yours?
                        - Yes
                            - Keep using that model
                        - No
                            - Choose another pre-trained embedding model
                        - No
                            - Train or fine-tune your own embeddings based on your data
                - Ensure similar embedding space for both queries and documents
                    - Use same embedding model for indexing and querying
                    - If using different embedding models, make sure they are trained on similar data

### Vector Search

- Introduction to vector stores
    - Vector database
        - A database that is optimized to store and retrieve high-dimensional vectors such as embeddings
        - In RAG, contextual information is stored in dense vectors
        - Vector databases are designed for efficient storage of vectors
        - Vector databases provide a query interface that retrieves most similar vectors
    - Query time and scalability
        - Specialized, full-fledged databases for unstructured data
            - Inherit database properties, i.e. CRUD
        - Speed up query search for the closest vectors
            - Uses vector search algorithms such as Approximate Nearest Neighbor (ANN)
            - Organize embeddings into indices
    - Common use cases for vector databases
        - RAG
        - Recommendation engines
        - Similarity search
    - Vector similarity
        - Distance metrics
            - The higher the metric, the less similar
                - Euclidean (L2) distance (most popular)
                - Manhattan (L1) distance
        - Similarity metrics
            - The higher the metric, the more similar
            - Cosine similarity is the most popular
    - Vector search strategies
        - K-nearest neighbors (KNN)
        - Approximate nearest neighbors (ANN)
            - Trade accuracy for speed gains
            - Examples of index algorithms:
                - Tree-based: ANNOY
                - Proximity graphs: HNSW
                - Clustering: FAISS
                - Hashing: LSH
                - Vector compression: SCaNN, Product Quantization (PQ)
    - HNSW: Hierarchical Navigable Small Worlds
        - Builds proximity graphs based on Euclidean (L2) distance
        - Traverses from query vector node to find the nearest
    - Product Quantization (PQ)
        - A technique used to compress high-dimensional vectors and perform efficient ANN searches
        - Useful in systems where memory usage and search speed are critical
        - Purpose
            - Vector compression
            - Efficient similarity search
            - Scalability
    - Reranking
        - A method of prioritizing documents most relevant to user query
            - Initial retrieval
                - Not all documents are equally important
                - Should use only the relevant documents
            - Reranker
                - Reorder documents based on relevance scores
                - The goal is to place most relevant documents at the top of the list
            - Reranking adjusts the initial ranking of retrieved documents to enhance the precision and relevance of search results
            - Reranking supports deeper semantic understanding based on documents’ actual relevance to the query
            - Rerankers
                - Private APIs: Cohere ReRank, Jina Rerank
                - Open-source: Cross-encoders, bge-reranker-base, FlashRank
            - Benefits & challenges
                - Benefits
                    - Select more relevant documents
                    - Improve accuracy of the response
                    - Reduce hallucinations
                - Challenges
                    - LLM must be called repeatedly, increasing cost and latency of RAG chain
                    - Implementing rerankers adds complexity to the RAG pipeline

### Agents and Cognitive Architectures

- Introduction to Agents
    - Non-agentic vs Agentic workflow
        - Non-agentic
            - LLM generates an answer based on actions defined
            - User prompt → Hard-coded actions → Final output
        - Agentic
            - Agent does research, write first draft, another model checks the daft
            - User prompt → Agent decides actions and their order → Final output
    - What is an Agent?
        - Agent is an application that can execute complex tasks by using LLM to define a sequence of actions to take
        - Agents replace hard-coded sequences of actions with query-dependent sequences chosen dynamically by LLMs
        - Core components
            - Task
            - LLM (brain)
            - Tools
            - Memory & planning
    - How does agent decide which actions to take?
        - Agent reasoning
            - Design patterns for agent reasoning
                - ReAct
                - Tool Use
                - Planning
                - Multi-agent collaboration
        - ReAct (Reason + Act)
            - Enables models to generate verbal reasoning traces and actions
            - Main states used in ReAct agent are:
                - Thought
                    - Reflect on the problem given and previous actions taken
                - Act
                    - Choose correct tool and input format to use
                - Observe
                    - Evaluate result of the action and generate next thought
        - Tool Use/ Function Calling
            - Agent interact with external tools and APIs to perform specific task
            - Agent reasoning skill decides which tolls to use and when/how to use them
            - Example tools
                - Research/search tools
                - Image
                - Document retrieval
                - Coding
        - Planning
            - Agents is able to dynamically adjust their goals and plans based on changing conditions
            - Tasks can be:
                - Single task
                - Sequential task
                - Graph task
        - Multi-agent collaboration
            - For complex tasks, it is difficult to scale the behavior with a single agent
            - It involves several agents working collaboratively, each handling different aspects of the task
            - Separating responsibilities to agents allows modularization
            - Can define agents specialized in solving specific problems
            - Each agent use the same or different (fine-tuned) LLMs for their expert task
    - Tools for building Agents
        - LangChain Agents
        - AutoGPT
        - OpenAI Function Calling
        - AutoGen
        - HF Transformers Agents
    - Multi-modal AI
        - Multi-modal models
            - Models with inputs or outputs that include data types beyond text
            - Common data types: image, audio, video

### Gen AI Evaluation Techniques

- Evaluation techniques
    - Base foundation model metrics: **Loss**
        - Foundation models predict next token
        - Loss measures the difference between predictions and the truth - train/validate the model
        - We can measure loss when training LLMs by how well they predict the next token
        - A few challenges:
            - Model will make prediction even they are not very confident (eg. hallucinations)
            - We can’t directly compute conversation accuracy since pre-training step is separate from alignment (optimizing for tasks)
            - Loss measures word prediction accuracy but doesn’t guarantee truly coherent or meaningful sentences
    - Base foundation model metrics: **Perplexity**
        - A metric measuring how well a model predicts a sample
        - Related to the model’s confidence in its predictions
            - Low perplexity = high confidence and accuracy
            - High perplexity = low confidence and accuracy
        - A sharp peak in the language model’s probability distribution reflects a low perplexity
        - It still doesn’t guarantee meaningful or accurate answers for specific tasks
    - Base foundation model metrics: **Toxicity**
        - LLMs can generate harmful output
        - We can compute toxicity to measure harmfulness:
            - Used to identify and flag harmful, offensive, or inappropriate language
            - Low toxicity = low harm
            - Uses a pre-trained hate speech classification model
    - Task-specific evaluation metrics
        - Metrics designed for evaluating specific tasks
        - When building AI systems, we’re concerned with completing specific tasks
            - Translating text
            - Summarizing text
            - Answering questions
        - MLflow support more specialized evaluation for tasks like:
            - Question answering
            - Text summarization
    - LLM evaluation metrics: Task-specific
        - To better understand how LLMs perform at a task, we need to evaluate them performing that specific task
        - NLP metrics
            - BLEU - for translation tasks
            - ROUGE - for summarization
        - **BLEU**: BiLingual Evaluation Understudy
            - BLEU compares translated output to a references, comparing n-gram similarities between the output and reference
        - **ROUGE**: Recall-Oriented Understudy for Gisting Evaluation (for N-grams)
            - ROUGE compares summarized output to a reference, comparing n-gram similarities between the output and reference
            - ROUGE versions
                - Some check single words, bigrams, or even the longest common sequence of words
                - ROUGE-Lsum
                    - Ignores punctuation, which is helpful when comparing summary outputs to reference paragraphs
        - Task-specific Evaluation Metric Similarities
            - Task-specific metrics
            - Applied to LLM output
            - Consider n-gram output rather than just unigram
            - Compare to reference datasets
    - Benchmarking: Types of data
        - Benchmarking → comparing models against standard evaluation datasets
        - Can use large generic datasets or curate on our own:
            - General LLMs are evaluated on large reference datasets (e.g. Standford Q&A is a generic dataset for general Q&A evaluation)
            - We should evaluate the LLM task on our own data, too
    - Mosaic AI Gauntlet
        - Well-curated set of benchmarks
        - Encompasses 35 different benchmark sources
        - Organized into 6 broad categories:
            - Reading comprehension
            - Commonsense reasoning
            - Problem solving
            - World knowledge
            - Symbolic problem solving
            - Language understanding
    - LLM-as-a-Judge
        - Ask LLM to do the evaluation for us
        - Given a set of rules to LLM, then apply them to automatically evaluate new responses
        - LLM-as-a-Judge techniques can utilize prompt engineering templating
            - Use few-shot examples with human-provided scores for more guidance
            - Provide more specific instructions of what good looks like
            - Provide a component-based rubric or more specific evaluation scale
        - Possible limitations
            - Lack of understanding and contextual awareness
            - Risk of metrics based on inaccurate or hallucinatory outputs
            - Bias and ethical concerns
        - Possible solution: **Human-in-the-loop**
            - Review the metrics generated by the LLM
            - Improve accuracy and handle ambiguities
        - Best practices
            - Use small rubric scales
                - LLMs excel in evaluation when the scale is discrete and small like 1-3 or 1-5
            - Provide a wide variety of examples
                - Provide a few examples to each score with detailed justification - this will give the evaluating LLM more context
            - Consider an additive scale
                - Additive scales (1 point for X, 1 point for Y, 0 point for Z = 2 total points) can break the evaluation task down into manageable parts for an LLM
            - Use high-token LLM
                - If being able to use more tokens, provide more context around evaluation to LLM

### Batch Deployment

- Batch processing generates predictions on regular schedule and writes the results out to persistent storage to be consumed downstream
- Batch deployment is the simplest deployment strategy
- Ideal for cases when:
    - Immediate predictions is not necessary
    - Predictions can be made in batch fashion
    - Number/volume of records/observations to predict is large
    - Pace at which input/records change or is received is > 30 mins
- Advantages
    - Cheapest deployment method
    - Ease of implementation
    - Efficient per data point
    - Can handle high volume of data
- Limitations
    - High latency
    - Stale data
    - Not suitable for dynamic or rapidly changing data
    - Not suitable for streaming data or real-time applications
- Batch inference from SQL using `ai_query()`
    - AI query is SQL method that lets run batch invocations on foundation model deployed within the platform
- Other batch inference methods using OSS integrations
    - TensorRT
        - Tensorflow-friendly SDK from Nvidia for high-performance batch inference on GPUs
    - vLLM
        - Transformer-friendly library for memory-efficient inference on GPUs
    - Ray on spark
        - Pythonic distributed computing Primitives for parallelizing/scaling Python applications

        - Reduction in manual oversight

        - Direct separation
            - Completed separate Databricks workspaces for each environment
            - Simpler environments
            - Scales well to multiple projects

            - One Databricks workspace with enforced separation
            - Simpler overall infrastructure requiring less permission required
            - Complex individual environment
            - Doesn’t scale well to multiple projects
    - Deployment patterns

            - Separate process needed for other code (inference, monitoring, operational pipelines)
        - Deploy code (recommended)
            - Code is developed in the development environment
            - Code is tested in the staging environment
            - Code is deployed in the production environment
            - Training pipeline is run in each environment, model deployed in production
